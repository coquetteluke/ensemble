## 2026-11-20 (the random permission failure in full test runs)

- Full `swift test` runs failed one random test with a permission error (`git commit`: "insufficient permission for adding an object to repository database .git/objects"; the terminal tests: `.spawnFailed(path: "/bin/sh", code: 13)`). Cause: `AgentToolsServer.start` set the process's file mode mask to 0177 around `bind` and put it back. The mask belongs to the whole process, so a folder any other thread made in those 40 microseconds got mode 0600 (no execute bit, it cannot be opened), and a child process started in them (`git`) kept the tight mask for its whole life. The suite starts the server 26 times in the same first seconds in which most tests make their folders. The app had the same small risk every time its tools server started.
- Proof of the cause, on one build with a run-time switch: the unchanged code, 3 full runs, no permission failure (one timing failure, see the last line); the mask held 10 ms longer, 2 runs, 12 and 31 failed tests, with both reported messages (10 of the 12 and all 31 were folder permission errors); the same 10 ms pause with no mask call, 2 runs, all passed. Every folder left behind with mode 0600 was born inside a logged mask window, or a few milliseconds after one when a child process made it. Five such folders from other sessions' runs that day were already in the temporary folder.
- Fix: no mask. The socket's folder is made by `mkdir` with mode 0700 in one step, which fails if anything is already at that path; then `bind`; then `chmod` 0600 on the socket before `listen`. No other user can reach the socket at any moment, because the folder is closed to them before the socket exists. The comment in `start` says why the order is safe. The old code took a folder that was already there and did not check its `chmod`.
- Tests: `AgentToolsServerTests.startingLeavesFoldersOtherThreadsMakeAlone` (four threads make folders while the server starts 50 times; it failed 15 of 15 times on the old code and passed 15 of 15 without the mask) and a guard, `ProcessWideStateTests`, that reads `Sources`, `Tests` and `Apps` and fails on a call to `umask`, `chdir`, `fchdir`, `setenv`, `unsetenv`, `putenv` or `changeCurrentDirectoryPath`. Tried with a planted file: each call was named, a comment and `posix_spawn_file_actions_addchdir` were not.
- Other process-wide state, searched for in `Sources`, `Apps` and `Tests`: nothing of the same kind. `signal(SIGPIPE, SIG_IGN)` in `AgentToolsBridge.run` is set once at the start of the helper's own process and never put back. `posix_spawn_file_actions_addchdir` in `PseudoTerminal` sets the child's folder only.
- Verification: five full `swift test` runs in a row on the fix, 1,311/1,311 tests in 162 suites each time, with the load average between 11 and 42.
- Not done: `TerminalLiveTests.shellPrintsColoursChangesFolderAndExitsCleanly` failed once on the old code at line 116 (`foregroundProgramName == "sleep"`) with the load average at 136. It is a timing check, not a permission error, and is not changed here. The Mac app was not rebuilt (no signature changed) and the opt-in live tests with a real engine were not run.
